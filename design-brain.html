why it matters

every team asks design the same small questions. which component? what spacing? is this on-brand? the answers lived in our design system, but nobody opens a document mid-task. they ask the designer, and they wait.

the system already had the answers. it just lived somewhere nobody worked — a figma library you have to go and open, a pdf two versions behind. so people guessed, or they queued. i closed that gap: if the answer lives in the repo, everyone has a designer on call.

the move

i wrote the design system the way engineers write specs — versioned, committed, reviewable.

instead of a pdf or a figma page, the design system became source files in the company repo: versioned, committed, sitting next to the code they govern. a change to the system is a pull request now, not an announcement.

inside the system

listing components was easy. ranking which one to reach for first was the real work.

brand.mdthe non-negotiables. voice, color, what digistay looks like and refuses to look like. everything built here passes through this.
components.mdthe 200+ list, prioritised. not an inventory — a ranking, so people reach for the right component first, not any component that fits.
tokens.mdthe numbers behind consistency. color, type and spacing as values, so output is measurably on-system, not approximately.
grid-spacing.mdhow things sit. the rhythm that makes a screen feel like ours before you read a word of it.
patterns.mdhow screens compose. components are vocabulary; patterns are grammar — list pages, detail pages, modals that behave.
icons.md + assets/the physical vocabulary. what exists, so nothing gets invented twice.

writing it was its own audit: you cannot hand-wave a priority in a spec someone will follow literally. every "it depends" i'd been carrying in my head had to become a rule i could defend.

design → dev

and when the fix is small, i ship it myself.

copy tweaks, spacing slips, token corrections: fixes that usually die in backlogs because a ticket costs more than the change. i make them in the frontend repo and open the pr. engineering reviews and merges. my b.tech finally earns its keep.

where this goes

the files are step one. the work now is adoption.

a design system only pays off if it is the easiest path, not the official one. so what's next is unglamorous and measurable: coverage for the modules not in it yet, usage checks so we know which components teams actually reach for and which ones quietly rot, and contribution rules so another team can add to the system without eroding it. honestly labeled: in progress — the parts that exist are already answering questions that used to wait for me.

decisions underneath

  1. write it where the work happens

    a pdf has to be remembered; a file in the repo is already open. same truths, different grammar — and this version can never be two versions behind.

  2. priorities, not inventories

    200 components listed is noise. 200 components ranked is judgment. the ranking is the design work.

  3. branding is the gate

    whatever gets built, it passes through the brand rules before it ships. taste isn't optional at scale — it has to be written down to survive.

  4. design owns the small diffs

    a ticket for a 4px fix costs more than the fix. push the pr, let engineering review, keep the backlog for real work.

  5. ship a file at a time

    one file shipped and used beats a whole system announced. the rollout is incremental on purpose.

what surprised me

the design system used to be a document people forgot. now it's the path of least resistance — the fastest way to build the thing is also the on-brand way. and writing it all down made me a sharper designer: every vague preference had to become a rule i could defend out loud.

the next design system won't be a pdf you're asked to read. it'll be the fastest way to build the thing. i'd rather be the designer who builds that than the one who maintains the pdf.
